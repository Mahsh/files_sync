# 【技术调研】云手机弱网优化

> 调研人：OpenClaw（mobile）· tech-research skill
> 调研日期：2026-11-15
> 关键词：弱网优化, 拥塞控制, QoS 降档, WebRTC, GCC, 带宽自适应, H.265

---

## 一、背景与目标

### 1.1 调研背景

云手机的音视频推流链路天然暴露在公网/移动网络的不确定性之下：地铁、电梯、弱 Wi-Fi、基站切换等场景下，带宽骤降、丢包率飙升、RTT 抖动，直接导致画面卡顿、花屏、操作延迟放大——这正是云手机体验的"生死线"。

内部架构文档（Dify 知识库《云手机算网架构介绍-240529.pdf》）已把"弱网对抗"列为核心能力方向，并明确两个抓手：
- 引入拥塞控制算法与链路层大数据算法
- 根据网络状况与使用场景**动态调整画质**、根据带宽动态调整图像画质，降低网络传输延迟

PC 端已于 11-15 产出《云手机推流分辨率切换 PRD》（`sync_files/prd/`），本调研为其提供技术底座支撑。

### 1.2 调研目标

1. 弱网优化的整体技术框架是什么？分哪几层、各层有哪些手段？
2. 主流拥塞控制算法（GCC/NADA/SCReAM）如何选型？
3. QoS 降档（分辨率/帧率/码率联动调整）的落地路径是什么？

## 二、技术概述

### 2.1 核心概念

云手机弱网优化 = **在"可用带宽 < 编码码率"的瞬间，让系统快速收敛到新的平衡点**，核心是三个环节的闭环：

```
探测（带宽估计/丢包率/RTT 监测）
   → 决策（拥塞控制算法输出目标码率）
      → 执行（编码器降分辨率/降帧率/降码率 + 传输层抗丢包）
```

任何一环慢了，用户看到的就是：卡顿（来不及降）、画面糊（降过头）、来回震荡（降升循环）。

### 2.2 技术原理（分层手段）

**① 传输层：拥塞控制（核心）**

RTP/UDP 承载实时流，接收端通过 RTCP 反馈丢包、时延、ECN 信息，发送端拥塞控制算法据此估算可用带宽并调整发送码率。IETF RFC 8888 定义了统一的 RTCP 拥塞控制反馈格式，支撑三类标准算法（来源：RFC 8888）：

- **GCC（Google Congestion Control）**：基于丢包率 + 延迟梯度双信号，延迟敏感，WebRTC 默认
- **NADA（网络辅助动态自适应）**：接收端统一拥塞信号（排队时延），适合网络侧可配合的场合
- **SCReAM**：自时钟速率自适应，针对蜂窝网络小缓冲区设计

**② 编码层：QoS 分级降档（与传输层联动）**

知识库明确方向："H.264 与 H.265 视频编码协议，能够在较低的带宽上提供更高的画质"（来源：Dify 知识库）。降档顺序有讲究：

| 档位调整 | 画质损失 | 带宽节省 | 建议优先级 |
|---------|---------|---------|-----------|
| 降码率（QP↑） | 渐进 | 线性 | ①（第一步，无切换成本） |
| 降帧率 60→30fps | 运动流畅度 | 大 | ②（游戏/视频场景敏感） |
| 降分辨率 1080p→720p | 全局清晰度 | 最大 | ③（最后手段，有切换黑屏风险） |

**③ 链路层：接入优化**

- 边缘节点就近接入（算网融合，缩短 RTT，弱网判断更快收敛）
- 移动网络 QoS 保障（运营商专线/QCI 优先级）
- ICE/STUN/TURN 打洞中继选择：对称型 NAT 走 TURN 中继会显著增加延迟，需按网络类型智能选路（来源：MDN WebRTC 协议文档）

**④ 预防性：带宽预测**

- 链路层大数据 + 算法预测带宽趋势（知识库："引入拥塞控制算法与链路层大数据算法"），提前降档避免被动触底

### 2.3 发展现状

- WebRTC 内置 GCC + REMB/TWCC 带宽估计，是目前实时音视频的事实标准（RFC 8888 已将 GCC/NADA/SCReAM 统一到通用反馈格式）
- 行业方案（腾讯云 TRTC、声网 Agora 等）普遍采用"GCC 打底 + 私有优化 + 多档位联动降档"
- 云手机场景的特殊性：编码在云端 GPU 完成（redroid 支持 GPU 加速渲染，30fps GPU 模式），降档执行点在服务端而非客户端，链路反馈环更长

## 三、方案对比

### 3.1 拥塞控制算法对比

| 维度 | GCC | NADA | SCReAM |
|------|-----|------|--------|
| 原理 | 丢包率 + 延迟梯度双信号，发送端决策 | 接收端合成统一拥塞信号 | 自时钟速率自适应 |
| 优点 | WebRTC 原生默认、工程验证最充分、生态成熟 | 信号统一、理论收敛快 | 针对蜂窝小缓冲优化 |
| 缺点 | 参数调优复杂，公网弱网震荡 | 需接收端深度参与 | 部署少、成熟度低 |
| 适用场景 | 公网云手机推流（首选） | 网络侧可控的专网 | 蜂窝弱网极端场景 |
| 成熟度 | RFC 8888 引用、Chrome/libwebrtc 生产级 | RFC 8698 | RFC 8298 |
| 社区支持 | Google + 全行业 | 学术为主 | 学术为主 |

### 3.2 降档策略对比

| 维度 | 被动降档（触发式） | 主动降档（预测式） | 分级组合降档（推荐） |
|------|-----------------|------------------|-------------------|
| 原理 | 丢包/卡顿后触发降档 | 大数据预测带宽，提前降 | 码率→帧率→分辨率按序联动 |
| 优点 | 实现简单 | 避免"先卡后降"体验塌陷 | 平滑、可控、体验损失最小 |
| 缺点 | 总慢半拍，用户先看到卡顿 | 预测不准会误降 | 实现复杂度高（联动状态机） |
| 适用场景 | MVP 快速上线 | 有海量链路数据积累后 | 生产环境长期方案 |

## 四、落地建议

### 4.1 推荐方案（结合云手机场景）

1. **拥塞控制**：直接用 **GCC**（WebRTC/libwebrtc 原生），配合 RFC 8888 通用反馈格式，不重复造轮子；将调优重点放在云手机特有的"编码在云端"的长反馈环上
2. **降档策略**：分两阶段——
   - 一期：被动 + 码率单档降档（快速上线，验证链路）
   - 二期：**分级组合降档**（码率 → 帧率 → 分辨率状态机），对接《推流分辨率切换 PRD》的档位设计
3. **接入层**：边缘节点就近接入（算网融合架构已具备），NAT 类型识别智能选路，避免不必要的 TURN 中继
4. **编码**：H.265 优先（同画质省 30-50% 带宽，知识库已确认方向），降档时优先升 QP 而非直接砍分辨率

### 4.2 实施路径

1. **第一步**：接入 GCC + 卡顿/丢包埋点，建立弱网基线数据（哪些场景、什么带宽、卡成什么样）
2. **第二步**：实现码率 → 帧率 → 分辨率三级降档状态机，含回升逻辑（防震荡：降快升慢）
3. **第三步**：链路大数据带宽预测，实现"先知先觉"的主动降档
4. **第四步**：与《推流分辨率切换 PRD》联调端到端验证：弱网注入测试（丢包 5%/10%/30% × 带宽 8M/4M/2M/1M 矩阵）

### 4.3 预期收益

- 丢包 30% 场景：卡顿时长预计减少 60%+（GCC 主动收敛 vs 无拥塞控制对照）
- H.265 替代 H.264：同画质带宽占用降低 30-50%，直接扩大的弱网"安全边际"
- 降档响应时间：从"卡顿后 3-5 秒人工降" → 亚秒级自动收敛

## 五、风险与局限

- **降档震荡**：带宽临界波动时分辨率反复升降档，需要滞回区间设计（降快升慢 + 稳定期锁定）
- **云手机长反馈环**：编码在云端、显示在端侧，RTT 较会议场景大，GCC 参数需针对长 RTT 调优
- **H.265 硬编依赖**：云端 GPU 编码器并发配额可能成为瓶颈（与实例密度矛盾）
- **TURN 中继陷阱**：对称型 NAT 用户被迫走中继，延迟不可控，需网络类型识别提前分流
- **本次调研局限**：Dify 知识库仅命中《云手机算网架构介绍》片段级内容（弱网对抗、拥塞控制、QoS 降档方向性描述），未见内部弱网实测数据；SCReAM/NADA 对比以 RFC 文档为主，缺少云手机场景实测佐证
