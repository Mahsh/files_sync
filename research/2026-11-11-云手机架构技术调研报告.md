# 【技术调研】云手机总体架构

> 调研人：OpenClaw（mobile）· tech-research skill
> 调研日期：2026-11-11
> 关键词：云手机, 虚拟化, ARM 服务器, 串流, redroid, cuttlefish

---

## 一、背景与目标

### 1.1 调研背景

云手机将 Android 系统整体运行在云端服务器上，用户通过音视频串流在本地终端远程操作。云OS（云端 Android）承载应用运行，算力、存储、网络全部在云端池化。为支撑后续研发（安装监控、串流优化、容器方案选型），需要对云手机总体架构做一次系统性梳理。

### 1.2 调研目标

1. 云手机的核心技术架构由哪几层组成？各层职责是什么？
2. 主流虚拟化方案（容器 vs 虚机）如何取舍？
3. 音视频串流链路的关键技术和现状如何？

---

## 二、技术概述

### 2.1 核心概念

云手机 = **云端虚拟化 Android 实例 + 实时音视频串流 + 远程控制**。用户在本地只看到解码后的画面，所有应用运行、渲染、存储都发生在云端 ARM（或 x86 + 指令翻译）服务器上。

### 2.2 技术原理（分层架构）

```
┌────────────────────────────────────────┐
│  终端层：H5 / 原生 App / WebRTC 播放器     │
├────────────────────────────────────────┤
│  接入层：信令服务（连接/认证/调度）          │
│         媒体转发（SFU/CDN/边缘节点）       │
├────────────────────────────────────────┤
│  云OS 层：Android 实例（应用运行环境）      │
│   - 容器方案：redroid（共享内核）           │
│   - 虚机方案：Cuttlefish/KVM（独立内核）   │
├────────────────────────────────────────┤
│  资源层：ARM 服务器集群 / GPU / 存储 / 网络 │
│   （算网融合：中心云 + 边缘节点就近接入）    │
└────────────────────────────────────────┘
```

- **终端层**：负责渲染画面回显与触控指令上行，通常基于 WebRTC 播放器或 H5 canvas
- **接入层**：信令服务负责实例调度与连接建立；媒体面走 RTC 网络或 CDN 分发
- **云OS 层**：核心差异点——容器方案共享宿主机内核，单机密度高；虚机方案每个实例独立内核，隔离性强
- **资源层**：ARM 服务器为主流（原生跑 ARM 应用无翻译损耗）；x86 方案需 libhoudini / libndk_translation 指令翻译层

### 2.3 发展现状

- 开源代表 redroid 已支持到 Android 16，覆盖 arm64 与 amd64，支持 GPU 加速渲染（androidboot.redroid_gpu_mode=host），在 Docker/K8s 环境单机可跑数十实例（来源：redroid-doc GitHub）
- Google 官方 Cuttlefish 定位虚拟设备（AVD），支持本地 Linux x86/arm64 与 GCE 云端部署，是 AOSP 官方测试基准方案（来源：google/android-cuttlefish GitHub）
- 国内厂商（华为云鲲鹏云手机、百度云手机、移动云手机等）均采用中心云 + 边缘节点的算网融合架构，主打云游戏、批量群控、自动化测试场景

## 三、方案对比

### 3.1 虚拟化层方案对比

| 维度 | redroid（容器） | Cuttlefish（虚机） | 定制虚机（厂商自研） |
|------|----------------|-------------------|---------------------|
| 原理 | Docker 容器共享宿主内核 | crosvm/KVM 每实例独立内核 | KVM/QEMU 深度定制 |
| 优点 | 密度高（单机数十实例）、启动快、资源占用低 | 隔离强、官方 AOSP 基准、架构仿真灵活 | 性能与兼容性可深度调优 |
| 缺点 | 共享内核，安全隔离弱；依赖 binder/ashmem 内核模块 | 密度低、资源开销大 | 研发成本高 |
| 适用场景 | 云游戏、群控、自动化测试 | 设备兼容性测试、CI | 规模化商用云手机 |
| 成熟度 | 开源社区活跃（支持到 Android 16） | Google 官方维护 | 各厂商自维护 |
| 厂商支持 | 社区 | Google | 华为/百度/移动等 |

### 3.2 串流方案对比

| 维度 | WebRTC（RTC） | 自研协议（TCP/UDP） | scrcpy（ADB 通道） |
|------|--------------|--------------------|--------------------|
| 原理 | RTP/UDP +拥塞控制，浏览器原生支持 | 私有协议，可深度优化 | ADB over TCP，H.264/H.265 + 事件注入 |
| 优点 | 低延迟（<100ms）、免插件、生态成熟 | 端到端可控、可定制 QoS | 极低延迟（35~70ms）、零后端依赖 |
| 缺点 | 带宽自适应受制于网络策略，弱网降档需自研 | 开发成本高，协议自维护 | 单对单，不适合公网商用 |
| 适用场景 | 商用云手机主流选择 | 大厂自研串流 | 开发调试、内部工具 |
| 成熟度 | 标准化（W3C/IETF） | 厂商私有 | 开源（Genymobile） |

注：scrcpy 实测延迟 35~70ms、30~120fps、无需 root；redroid 计划从 cuttlefish 移植 WebRTC 方案（来源：scrcpy / redroid-doc GitHub）

## 四、落地建议

### 4.1 推荐方案（结合云手机研发场景）

- **虚拟化层**：以 **redroid 容器方案**为起点。密度高、迭代快，与现网"应用安装监控"等云OS 侧需求（共享内核层做 hook 更容易）契合；对隔离性要求高的场景（金融、政务）再引入虚机方案
- **串流层**：商用链路走 **WebRTC**（弱网自适应、浏览器直达）；研发调试链路保留 **scrcpy**（零依赖、延迟最低）
- **边缘接入**：算网融合架构，中心云跑重负载实例，边缘节点承接对延迟敏感的实时操作

### 4.2 实施路径

1. **第一步**：搭 redroid 集群 + scrcpy 调试通道，验证应用安装/运行/监控全链路
2. **第二步**：接入 WebRTC 串流（可复用 cuttlefish 的 webrtc 前后端），压测弱网自适应
3. **第三步**：接入算网调度（中心 + 边缘），按负载动态分配实例

### 4.3 预期收益

- 单机密度相比虚机方案提升 3~5 倍（容器共享内核，据 redroid 社区数据）
- 调试链路延迟 <70ms（scrcpy 实测）
- 商用链路弱网可用性依赖 WebRTC 自适应，目标丢包 30% 下仍可操作

## 五、风险与局限

- **安全隔离**：容器共享内核，恶意应用提权可能影响同机其他实例——需配合 SELinux、namespace 加固，或高安全场景用虚机
- **内核依赖**：redroid 需要 binder_linux / ashmem_linux 模块，宿主机内核版本需满足要求
- **GPU 虚拟化**：GPU 直通/共享调度是密度瓶颈，需按 GPU 资源做实例配额
- **x86 兼容性**：x86 服务器跑 ARM 应用依赖指令翻译（libndk_translation），部分应用存在兼容性长尾
- **本次调研局限**：Dify 知识库因网络原因（api.dify.ai TLS 握手超时）未能检索，历史内部资料（如《云手机算网架构介绍》）未纳入；本报告仅基于开源公开资料
